תוכנית עבודה — מעבר ל-API של Turso (HTTP)

carinfo-bot · עודכן לאחרונה: 4 בנובמבר 2026 · מסמך פנימי להמשך עבודה (לבעל המערכת ולמי שימשיך את הפיתוח)

בקצרה: הספרייה הנייטיבית של Turso (libsql_experimental) מחזיקה את ה-GIL של פייתון לאורך כל סיבוב רשת, ולכן כל שאילתה מקפיאה את התהליך כולו (הבוט, ה-API ו-event loop). המעבר ל-API של Turso ב-HTTP דרך httpx.AsyncClient נותן שאילתות אסינכרוניות באמת, חיבור פתוח (keep-alive) ואפשרות לשלוח כמה פקודות בבקשה אחת. מוצע לבצע בשלבים, מאחורי מתג בסביבה, כך שאפשר לחזור לספרייה הנוכחית בלי commit.

1. למה (רקע וראיות)

  • התסמין: חיפוש ב-WebApp נתקע שניות עד עשרות שניות בשלב "מרכיב את הדוח", במיוחד אחרי deploy.
  • הלוג (3 בנובמבר, שירות הבוט ב-Render):

  • קוד המקור של libsql-python (src/lib.rs): execute() רץ ב-rt().block_on(...) בלי לשחרר את ה-GIL. לכן 6 התהליכונים ב-ThreadPoolExecutor לא נותנים מקביליות, וכל סיבוב רשת (כ-150–500 מילישניות) עוצר את כל התהליך.

4. תכנון

4.1 עקרון

  • כל הקוד משתמש רק ב-await execute(sql, args) (כ-259 אתרי קריאה) שמחזיר .rows (רשימת tuples) ו-.columns (אובייקטים עם .name). רק src/db.py נוגע בחיבור עצמו. לכן אפשר להחליף את המימוש בלי לגעת בשאר הקוד.
  • כתובת file: (פיתוח מקומי ובדיקות) ממשיכה לרוץ על libsql או sqlite כמו היום. ה-HTTP רק לכתובות libsql:// / https://.
  • מתג סביבה: TURSO_HTTP=1 מדליק את הלקוח החדש. ברירת המחדל כבויה, כך שה-deploy הראשון לא משנה כלום.

4.2 הלקוח החדש (src/db.py)

  • httpx.AsyncClient יחיד לכל התהליך, http2=True אם זמין, timeout של 15 שניות, keep-alive.
  • execute(sql, args): בקשת pipeline אחת עם execute + close; המרת הטיפוסים לפי הטבלה בנספח; אותה מחלקה _Result.
  • execute_many([(sql, args), …], transactional=False): פקודות רבות בבקשה אחת (לאתחול, למונה ההזמנות, ולכתיבות שמגיעות יחד).
  • ניסיון חוזר אחד על שגיאות רשת/5xx (כמו הלוגיקה של _CONN_ERRORS היום), עם backoff קצר. שגיאות SQL (error בתשובה) מוחזרות כחריגה, כמו היום.
  • הסרת _executor ו-_local עבור ה-HTTP. ה-ThreadPoolExecutor ישאר רק לנתיב file:.

6. פריסה ושחזור

  1. deploy עם מתג כבוי: אפס שינוי התנהגותי; מוודאים שהבוט עולה.
  2. הדלקה: ב-Render ← Environment ← TURSO_HTTP=1, והפעלה מחדש.
  3. בדיקות אחרי הדלקה (5 דקות): חיפוש בבוט, חיפוש ב-WebApp, רכישה/הענקת מנוי (כתיבה), פאנל ניהול.
  4. שחזור: להסיר את TURSO_HTTP (או לשים 0) ולהפעיל מחדש. אין צורך ב-commit ואין שינוי סכימה.

8. חלופות שנשקלו

  • Embedded replica (קבצים מקומיים עם סנכרון מ-Turso): קריאות מקומיות כמעט מיידיות. נדחה לעת עתה: כתיבות עדיין עוברות לשרת ועדיין מחזיקות GIL, התיעוד מזהיר מפני פתיחת הקובץ בזמן סנכרון (בעיה עם חיבורים מרובי תהליכונים), והדיסק ב-Render אפמרלי (סנכרון מלא בכל הפעלה).
  • תהליך נפרד לשכבת ה-DB: פותר GIL, אבל מוסיף מורכבות תפעולית. ה-HTTP נותן אותו יתרון בפשטות.
  • הישארות עם autocommit בלבד: כבר בוצע. חוסך שני סיבובים לכתיבה אבל לא מסיר את ההקפאה.

9. רשימת בדיקה לקבלה

  • אתחול הסכמה מדלג כשלא השתנה (נבדק מקומית: 146 → 30 פקודות)
  • חיבור autocommit (נבדק מקומית עם דוגמה)
  • לקוח HTTP עובד עם שרת מדומה: SELECT, INSERT, UPDATE, NULL, מספר שלם גדול, טקסט בעברית
  • שגיאת SQL מחזירה חריגה עם הודעה קריאה
  • ניסיון חוזר בשגיאת רשת ו-5xx; אין ניסיון חוזר בשגיאת SQL
  • אתחול הסכמה בבקשה אחת ומדלג כשלא השתנה
  • מונה הזמנות אטומי בבקשה אחת
  • כל בדיקות ה-API מקצה לקצה עוברות בשני המצבים (TURSO_HTTP=0 ו-=1)
  • פרודקשן: db-writes < שנייה, ללא "missed by" בלוג, עלייה < 10 שניות אחרי deploy
  • עדכון CLAUDE.md (סעיף "Turso / libsql performance notes" ומשתנה הסביבה החדש)

10. נספחים

א. פרוטוקול ה-pipeline (לאימות מול התיעוד הרשמי לפני המימוש)

מה שמופיע כאן נכתב מזיכרון של התיעוד ומקוד הספרייה. לבדוק בתחילת שלב 1 את docs.turso.tech/sdk/http/reference.

POST https://<db>.turso.io/v2/pipeline
Authorization: Bearer <TURSO_AUTH_TOKEN>
Content-Type: application/json

{ "requests": [
    { "type": "execute",
      "stmt": { "sql": "SELECT * FROM users WHERE user_id = ?",
                "args": [ {"type": "integer", "value": "777"} ] } },
    { "type": "close" } ] }

→ { "results": [
      { "type": "ok", "response": { "type": "execute", "result": {
          "cols": [ {"name": "user_id"}, … ],
          "rows": [ [ {"type": "integer", "value": "777"}, {"type": "text", "value": "…"} ] ],
          "affected_row_count": 0, "last_insert_rowid": null } } },
      { "type": "ok", "response": { "type": "close" } } ] }

שגיאה:  { "type": "error", "error": { "message": "…", "code": "…" } }
פייתוןל-API (קלט)מה-API (פלט)
None{"type":"null"}null → None
int{"type":"integer","value":"123"} (מחרוזת)integer → int(value)
float{"type":"float","value":1.5}float → float

כמה בקשות execute באותה בקשת pipeline רצות ברצף על אותו stream, ולכן אפשר לשלב BEGIN ... COMMIT כפקודות בתוך הבקשה לטרנזקציה אטומית.
